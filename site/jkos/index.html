jkOS

jkOS is a self-hosted suite of web apps on TrueNAS SCALE: a portal, single sign-on, tasks and calendar, music and audiobooks, and a deploy console. It runs in Docker behind nginx with TLS, with separate staging and production.

Each security control is enforced in code and covered by a test. The three sections below show how sign-in, the audit log and deployments work.

Single sign-on and sessions

Sign-in and sessions
How it works · step throughRS256 · audience · 15 min · rotation
  1. You to jkAuth: sign inYou sign in once, at jkAuth.
  2. jkAuth to you: access token and refresh tokenjkAuth signs the access token with RS256. The private key never leaves jkAuth.
  3. You to the app: request with the access tokenThe browser sends the access token to an app.
  4. The app checks the tokenThe app verifies the signature with jkAuth's public key, then checks the issuer, the expiry and that the token names this app.
  5. The access token expiresThe access token is valid for 15 minutes.
  6. You to jkAuth: refreshRefreshing returns new tokens. The old refresh token is retired and can't be used again.
  7. Attacker to jkAuth: replay the old refresh tokenSomeone presents a refresh token that was already used.
  8. jkAuth revokes the sessionjkAuth revokes every token from that sign-in and logs a refresh_reuse event. The session rows stay, marked reuse.
  9. jkAuth to attacker: rejectedThe attacker is rejected. You sign in again.
  1. jkAuth signs tokens with RS256. The private key stays in jkAuth, and other apps verify with the public key. tokens.js
  2. Each token lists the apps it is valid for, and an app rejects a token meant for another app. Node backends refuse to start in production without this check. auth.js
  3. Access tokens expire after 15 minutes. Refresh tokens rotate on every use, and reusing an old one revokes the whole session. Sessions also have a maximum lifetime. tokens.js
  4. Revoked sessions are kept with a reason (logout, reuse or absolute_timeout), not deleted. Database triggers block reuse of a sign-in code and stop a session moving to another client. db.js
  5. security.mjs starts the real server and tries token replay, expired sessions and a token issued for the wrong app. security.mjs

auth_events table
How it works · select a stepone trusted proxy

What each step records:

  1. RequestNothing yet. An IP address the client claims for itself is ignored.
  2. nginxThe client's real IP. jkAuth trusts exactly one proxy hop, and won't start if that setting changes.
  3. jkAuthThe decision: allow, deny or lock the account.
  4. Audit tableOne row per event: time, type, user, IP and details. Users read their own rows. Admins read all of them.

Deployments

Staging to production
How it works · select a stagetags = controls
  1. Test suiteThe full test suite is run before staging. It is run by hand: there is no CI yet, and CONTROLS.md lists that as a known gap.
    • Run by hand, no CI yet
  2. StagingStaging has its own sign-in. nginx checks with jkAuth before serving any staging page, and lets in admins only.
    • nginx asks jkAuth first
    • Separate staging sign-in
  3. PromoteOnly an admin can deploy. Production is reset to the exact commit staging ran. There is no merge step, and the server can't push code.
    • Deploy requires admin
    • Exact commit, no merge
    • Server can't push code
  4. ProductionThe nginx config is tested before nginx restarts. The deploy fails if any container isn't running or reports itself unhealthy.
    • nginx config tested first
    • Every container healthy
    • Separate production sign-in
  1. Staging is admin-only: nginx checks with jkAuth before serving any staging page. gen-nginx-weave.mjs
  2. Staging and production use separate sign-ins, so a staging login doesn't work in production. index.js
  3. Deploying requires an admin account. main.py
  4. Production is reset to the exact commit staging ran. There is no merge step, and the server can't push code. A deploy fails if any container isn't running or is unhealthy. lib-deploy.sh
